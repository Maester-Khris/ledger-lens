# Chat Eval Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a corpus-wide answer key (about 300 cases), sweep the retrieval threshold and a logprob confidence
signal, and run and judge one final `gpt-4.1` run that produces publishable rates with margins.

**Architecture:** A pipeline of separate CLI stages under `backend/scripts/evalkit/`, each reading only the previous
stage's JSONL file under `backend/reports/eval-key/` or `backend/reports/eval-final/`. Pure logic (case schema,
statistics, metrics) lives in framework-free modules; provider calls go through one OpenAI-compatible client factory
with a per-model token limiter. The only application change is an additive `confidence` field on the chat's final
event, from the answer call's logprobs.

**Tech Stack:** Python 3.12, LangChain `ChatOpenAI` (OpenAI, Groq and Anthropic OpenAI-compatible endpoints), agy CLI
(`gemini-4-argon-high`), Claude Code headless (`claude -p`), pytest.

**Spec:** `docs/superpowers/specs/2026-10-21-chat-eval-design.md`

## Global Constraints

- Python env: `/home/niki/Documents/workenv/pydev/bin/<tool>`, run from `backend/`; never a repo `.venv`.
- Only redacted text leaves the machine: writer, checker and judge inputs come from `document_elements.text_redacted`
  and the chat's redacted answers/quotes; never revealed values.
- Model roles, fixed: writers `qwen/qwen3.8-27b` and `openai/gpt-oss-120b` (Groq); checker `gemini-4-argon-high`
  (agy); tiebreak = the other Groq family from the case's writer (`openai/gpt-oss-20b` for qwen cases,
  `qwen/qwen3.8-27b` for gpt-oss cases); judge `claude-sonnet-5-5`; system under test `gpt-4.1-2025-04-14`.
- Groq limits per model: 30 requests/min, 8,000 tokens/min, 1,000 requests/day, 200,000 tokens/day.
- Threshold sweep range: 0.38 to 0.50 inclusive, step 0.01.
- Case mix targets: answerable 190, out_of_corpus 20, false_premise 20, underspecified 20, nonsense 20, off_topic 20,
  explained 10; the existing 37 cases in `tests/eval/golden.json` are carried in and count toward these targets.
- Margins: Wilson 95% interval on every rate; Clopper-Pearson upper bound for the anchor error rate (as X1).
- Every paid OpenAI or Anthropic API call: the stage prints its estimate and refuses to run without `--yes`; the
  executor stops and asks the owner before passing `--yes`, then records the measured cost in
  `artifacts/2026-10-17-x1-spend-ledger.md`.
- Frozen prompts: every prompt and instruction file under `backend/scripts/evalkit/prompts/` is committed before the
  stage that uses it runs; stage outputs record the git hash of the prompt file they used.
- Commits: conventional commits, explicit `git add`, no AI attribution lines.
- **Scripts, checkpoints, resume (owner rule):** every stage is a plain CLI command, never driven turn by turn from a
  chat context. Every stage that calls a model writes each finished item to `<out>.partial.jsonl` as soon as it is
  done (append and flush per item), skips items already there when re-run with the same arguments, and only at the end
  moves the result to its final file atomically (`os.replace`). A crash or quota stop is resumed by re-running the
  same command; nothing finished is paid for twice. Each stage ends by printing one JSON summary line (counts, failures,
  spend estimate, output path) so the operator reads one line, not the logs.
- Code tasks go through claude-agy-orch (Gemini on `tmp/agy-*`, Claude reviews and fast-forwards); Task 3 (app code)
  is Claude's.

## Review Focus

1. A Groq 429 or a malformed JSON reply from a writer: the stage retries once after the limiter's window, then records
   the document as failed and continues; it never writes a half-parsed case. (Task 4 test.)
2. agy returning a verdict file that omits cases or adds unknown case ids: the batch is rejected whole and re-run
   once; unknown ids are never merged. (Task 5 test.)
3. A chat turn that ends in `error` (provider rate limit) during the final run: retried once after 65 s like the
   golden runner, and marked `retried`; a second error is recorded as `error`, excluded from rates and counted.
   (Task 8 test.)
4. A judge reply citing a citation id that is not in the case's citations: that entry is dropped and the case is
   flagged `judge_inconsistent`; flagged cases are counted in the report. (Task 9 test.)
5. A rate with n = 0 (for example a junk category emptied by drops): the report prints `n=0` and no rate, never
   divides by zero. (Task 10 test.)
